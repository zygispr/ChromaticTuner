# Phase 0 Research: App Icon Coverage

**Feature**: `008-app-icon-coverage` | **Date**: 2026-08-15

Everything below was checked against the installed toolchain in this workspace, not against
documentation alone. Where a claim is about a vendor's behaviour, the file and line that proves it are
named.

---

## D1 — Root cause: Expo writes a blank white square when no icon is configured

**Decision**: The mobile defect is not a missing file. It is a missing four lines of configuration, and
Expo's own fallback is what fills the gap with a placeholder that looks deliberate.

**Evidence**: `node_modules/@expo/prebuild-config/build/plugins/icons/withIosIcons.js`,
`generateUniversalIconAsync`:

```js
} else {
  // Create a white square image if no icon exists to mitigate the chance of a submission failure to the app store.
  source = await createSquareAsync({ size });
}
```

That `else` branch is the icon this app currently ships. Confirmed three ways: `app.config.ts` declares
no `icon`, no `ios.icon` and no `android.adaptiveIcon`; the resolved config agrees —

```
$ pnpm --filter @chromatic-tuner/mobile exec expo config --json --type prebuild
icon: None   ios.icon: None   android: { package, versionCode, permissions }   # no adaptiveIcon
```

— and the artefact it produced,
`apps/mobile/ios/ChromaticTuner/Images.xcassets/AppIcon.appiconset/App-Icon-1024x1024@1x.png`, opens as a
blank white 1024×1024.

**Why this went unnoticed for four features.** The fallback is *silent and successful*. Expo's comment
says it exists "to mitigate the chance of a submission failure" — it is designed to make a build with no
icon build anyway. Nothing warns; the native project is git-ignored generated output, so nobody reviews
it; and `004` gated the store **fields**, which were correct. The one artefact that would have shown it
is a screenshot of a home screen, and the screenshot gate captures the app's own screen.

**Alternatives considered**: Committing an `AppIcon.appiconset` by hand into `apps/mobile/ios/`. Rejected
outright — that directory is in `.gitignore` (line 77) and `prebuild` regenerates it, so the fix would
survive until the next clean build and then vanish. FR-175 exists to name this.

## D2 — The mobile icon assets live in `apps/mobile/assets/`, not referenced out of `listing/`

**Decision**: `generate-icons.mjs` emits three new PNGs into `apps/mobile/assets/`, and `app.config.ts`
names them with project-relative paths (`./assets/icon.png`). It does **not** point at
`../../listing/assets/*`.

**Rationale**: three reasons, in order of weight.

1. **Expo hands the path to an image library, not to a resolver.** `@expo/image-utils`'s
   `downloadOrUseCachedImage` returns any non-`http` string unchanged
   (`build/Download.js:26-37`), and it is then passed straight to sharp/jimp — so the string is resolved
   against the **current working directory**, not against the project root, despite the surrounding API
   taking `projectRoot` as an argument. A path that climbs out of the project works only for as long as
   every tool that shells out to `expo` happens to `cd` to `apps/mobile` first. That is true of
   `pnpm --filter … exec` today and is not a property anything asserts.
2. **It would invert a dependency the repo states.** `CLAUDE.md`: "`listing/` is outside that graph and
   depends on nothing." `app.config.ts` already imports `listing/store-listing.json`, but that is *data,
   read by Node, at config time*, and `004` justified it explicitly. Bytes fed into a native build are a
   different kind of dependency: it would make `apps/mobile` unbuildable without `listing/`.
3. **It matches the structure both apps already use.** `apps/web/public/icon.svg` is a separate committed
   file from `listing/assets/icon-play-512.png`, generated by the same script from the same mark. The
   mobile app getting its own `assets/` directory is the existing pattern, not a new one.

**Cost accepted**: three more committed generated PNGs, two of which are pixel-identical in intent to
files already in `listing/assets/`. That is duplication of *output*, not of *source* — one generator, one
mark, one palette — and D5's manifest makes the duplication checkable rather than merely tolerated.

**Alternatives considered**: A build step that copies from `listing/assets/` into `apps/mobile/assets/`
at prebuild time. Rejected under Principle II — it adds a step, a failure mode and an ordering
constraint to save three files that change about once a year.

## D3 — Android uses `backgroundImage`, not `backgroundColor`, and that is a lint constraint

**Decision**: `android.adaptiveIcon` gets `foregroundImage` and `backgroundImage`. It does not get
`backgroundColor`.

**Rationale**: `backgroundColor` takes a hex string, and a literal hex anywhere in `apps/**` is an ESLint
error in this repo. The alternatives to a literal are both bad: importing `@chromatic-tuner/tokens` into
`app.config.ts` puts a workspace TypeScript package into Expo's config loader for one string, and
suppressing the rule defeats the rule that exists precisely to stop colours being transcribed. A
generated solid-colour PNG carries the same value with no literal anywhere, and it comes out of the same
palette read the rest of the artwork comes from.

**Verified inert**: `withAndroidIcons.js` writes `#ffffff` into `colors.xml` as `iconBackground` whenever
`backgroundColor` is absent, which reads alarming. It is not: `createAdaptiveIconXmlString` selects
`@mipmap/ic_launcher_background` over `@color/iconBackground` whenever a `backgroundImage` exists
(`withAndroidIcons.js:238`), so nothing references the white.

**Also verified**: `adaptiveIcon` must be declared at all. From the same file's own comment — "If the
user only defined icon and not android.adaptiveIcon, then skip enabling the layering system, this will
scale the image down and present it uncropped." A top-level `icon` alone gives Android a shrunken,
unmasked tile, which is not FR-174.

## D4 — iOS gets the opaque icon, and the reason is Expo's compositing, not just Apple's rule

**Decision**: `icon` (top level) points at the opaque, full-bleed, un-rounded 1024 — the same geometry as
`listing/assets/icon-ios-1024.png`. The transparent adaptive foreground must never be fed to it.

**Rationale**: `generateUniversalIconAsync` passes `removeTransparency: true` and
`backgroundColor: '#ffffff'` for the base variant. Hand the transparent foreground to it and the mark is
composited onto **white** — silently, with no error, producing a wrong-but-plausible icon. Apple's
no-alpha rule is the better-known half; Expo's flatten-onto-white is the half that would actually bite,
because it produces a shipped icon rather than a rejection.

`resizeMode: 'cover'` also crops a non-square source, so the source must be square. It is.

## D5 — PNG provenance: a sidecar manifest, because a raster cannot carry a comment

**Decision**: `generate-icons.mjs` writes `listing/assets/artwork.json` alongside the artwork, recording
for every artefact it emits: the path, the pixel dimensions, a SHA-256 of the bytes, and the palette
values the artefact was drawn from. `verify-listing.mjs` checks that every listed file exists with a
matching digest, that every artefact the generator emits is listed, and that every recorded palette value
still appears in the built `--ct-*` token block.

**Rationale**: FR-179 asks for the guarantee L11 already gives the SVGs, extended to rasters. L11's two
checks do not transpose:

- "every colour literal is a palette value" — a PNG has no literals, only pixels.
- "the file carries the generator's provenance marker" — a PNG has no comments the current encoder writes.

The manifest reproduces both properties exactly, in the same two-check shape and for the same stated
reason. The digest catches hand-authoring (L11's check 2 — the D5-of-`004` defect, where values were
transcribed *correctly* and drifted later). The recorded palette catches drift (L11's check 1 — a token
moves, the artwork is not regenerated, the record still names last season's colour).

It also closes something `004` left manual. V34 is "regenerate and see no diff", manual because it needs
a browser — and `pnpm listing:assets` cannot run on CI's Ubuntu runners. A committed digest lets CI prove
the committed bytes are the ones the generator last produced **without launching anything**.

**Alternatives considered**:

- *Decode the PNGs and check their pixels against the palette.* Rejected. It needs a decoder;
  `generate-icons.mjs` already carries one (`unfilter`), so this would be its second copy, and
  anti-aliased edges mean the check has to degrade into "sample these particular pixels", which is a
  gate that passes on a shifted mark.
- *A PNG `tEXt` chunk as the provenance marker.* Genuinely the more elegant answer, and rejected only on
  cost: the generator has two output paths (Chromium's bytes passed through, and the re-encoded
  alpha-stripped path), so the chunk would have to be injected into both. The manifest covers more —
  it records the palette too — for less code.
- *Digest only, no palette record.* Rejected: it proves the file is untouched and says nothing about
  whether it is current, which is half the requirement.

## D6 — `apple-touch-icon` needs a PNG, and it must not be the rounded one

**Decision**: generate `apps/web/public/apple-touch-icon.png` at 180×180 — opaque, full-bleed, **square,
with no pre-applied corner rounding** — and point the existing `<link rel="apple-touch-icon">` at it.

**Rationale**: three separate constraints, each of which alone produces a visibly wrong tile.

1. **Format.** Safari on iOS and iPadOS does not accept SVG for `apple-touch-icon`; the current
   reference silently degrades to a screenshot of the page. (SVG *is* supported for the tab favicon
   since iOS 15, which is why `icon.svg` stays exactly as it is.)
2. **Transparency.** iOS composites a transparent touch icon onto **solid black**. The source must be
   the opaque variant.
3. **Rounding.** iOS applies its own superellipse mask. `apps/web/public/icon.svg` is generated with
   `rounded: true` (`rx = size × 0.1875`) because it is used as a favicon and a PWA icon, neither of
   which masks. Reusing it here would be masked *again*, cutting the already-rounded corners and letting
   the page background show through at four points.

180×180 is the largest size iOS requests (60pt at @3x); iOS downscales for every smaller slot, so one
file serves all of them.

**Alternatives considered**: emitting a full ladder of `apple-touch-icon-{57,72,114,152,180}.png`.
Rejected under Principle II — every iOS version this project supports downscales a single 180 correctly,
and the ladder is five more files to keep in a manifest.

## D7 — The web manifest gains PNG icons; the SVGs stay

**Decision**: add `icon-192.png` and `icon-512.png` (opaque, un-rounded, full-bleed) to the generated web
manifest, keeping both existing SVG entries. The 512 is declared `purpose: 'maskable'` as well, drawn at
the safe-zone scale.

**Rationale**: Chromium's own guidance is that a manifest must provide at least a 192×192 and a 512×512
raster, and that an SVG icon should always be paired with a rasterised fallback for engines that do not
support one. This is the same class of defect as D6 — a platform that cannot use the icon substitutes
something rather than reporting a problem — and this feature exists to remove that class, not one
instance of it.

**Open risk, to verify manually rather than assert**: there are reports of a Chromium bug in which an SVG
manifest icon declared `sizes: "any"` can make PWA installability fail outright
(`issues.chromium.org/issues/40925759`). This repo's manifest declares exactly
`{ src: '/icon.svg', sizes: 'any', … }`. The tracker requires a sign-in and the report could not be read,
so this is recorded as a thing to observe, not as a finding. Adding the rasters is the correct action
whether or not the bug is real, and V75 checks installability on a real Chromium either way.

> **Observed, and it is a finding** (T041 — see "What the release gates found" in `tasks.md`). The app
> did not install in Chromium at all. The trigger is narrower than reported: any icon whose `purpose`
> includes `any` declaring the `any` **size** keyword — Chromium picks it, cannot size it, and does not
> fall back to the rasters. The last sentence above is therefore too optimistic: adding the rasters did
> not rescue it. `/icon.svg` now declares `512x512`; `/icon-maskable.svg` keeps `any`, which is safe
> because installability never considers a maskable-only icon.

## D8 — Deliberately out of scope, each with the reason

- **iOS dark and tinted icon variants.** `ios.icon` accepts `{ light, dark, tinted }` in this Expo
  version. Skipped: the mark is already drawn from the dark palette, so a "dark variant" would be the
  same picture, and a tinted variant is a monochrome silhouette — see the next item for why that is the
  wrong thing for this mark. Adding a second variant is buildable later from the same template.
- **The Android 13+ monochrome themed icon.** Skipped deliberately, and this one is a design judgement
  rather than an economy. The mark carries its meaning in **three colours** — a flat dot, a sharp dot,
  and an in-tune centre marker. Monochrome flattens all three to one silhouette, which keeps the shape
  and deletes the point. Omitting `monochromeImage` makes Android fall back to the full-colour adaptive
  icon when themed icons are on, which is strictly the better of the two pictures.
- **Splash and launch screens.** A different surface with different timing constraints — `005` routed
  first-frame appearance through the launch screen on purpose. Noted for a future feature: the launch
  screen is likewise unconfigured and inherits a platform default rather than `--ct-background`.
- **A favicon `.ico`.** No browser this project supports requires one, and `icon.svg` plus the new PNGs
  cover every documented fallback path.

## D9 — Where each new gate goes, and why there

The three defects need three gates, and all three have an existing home. Nothing new is built to hold
them.

| Defect | Gate | Why there |
| --- | --- | --- |
| Mobile configured with no icon | `verify-listing.mjs`, via `resolvedMobileConfig()` | It already shells out to `expo config --json --type prebuild` for L12. The **resolved** config is what reaches the native project — a check against `app.config.ts` source would agree with the source whatever a plugin did. `apps/mobile/__tests__/app-config.test.ts` asserts the same at the source, matching how `004` layered L12. |
| Web icon in an unusable format | `apps/web/e2e/metadata.spec.ts` | Its existing test collects every icon URL from the live document and asserts each resolves. The extension is one assertion on the *format* per `rel`, in the test that already has the URLs. |
| Submission checklist claims something false | `verify-listing.mjs` | It already reads `submission.md` and `limits.json` together. The new artefacts get entries in `limits.json`'s `assets.files`, which is the data the assets group is driven by — so the file table extends without new code. |

The service-worker precache list in `apps/web/vite.config.ts` also hard-codes `/icon.svg` and misses
`/icon-maskable.svg` today. New icons must be added there or an installed app is offline-capable with
missing artwork.
